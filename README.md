# SWARMSY — DIZ-A-REMIX

**A beginner-first creator operating environment built on AnythingLLM and led by SPARKY.**

SWARMSY helps ordinary people create or strengthen a distinctive identity, project, character, business, campaign or creative direction without needing to understand AI tools.

The user provides the first spark. SPARKY guides the process, keeps the real project context, separates suggestions from approved decisions, preserves continuity and helps the selected local or API-backed model turn that spark into stronger possibilities.

> **The selected AI helps SPARKY think. SPARKY manages the user’s questions, ideas, approved decisions and saved project memory.**

## Read This First

SWARMSY is not a new language model.

It is not a generic chatbot skin, fixed branding template, complete prewritten encyclopaedia or attempt to recreate ChatGPT, Claude, Gemini or another foundation model.

SWARMSY is an opinionated beginner product built on AnythingLLM.

- **AnythingLLM** provides broad model connectivity, document retrieval, workspaces and advanced general-purpose AI capability.
- **SPARKY** is the permanent visible operator, guide and project-context manager.
- **The selected model** provides local or API-backed reasoning and generation capability.
- **Starter Wiki Packs** provide minimum situational context, boundaries and action awareness.
- **User-grown project intelligence** develops from the user’s own rules, documents, laws, sources, contacts, proof, methods and experience.
- **Memory Locks** preserve approved truths and decisions.
- **Proof Review** separates ideas, proposals, completed work and supported public claims.
- **Crypto Moonboys** is the connected public creator movement, community, knowledge world and shared cultural record.

The public and private sides have different jobs:

> **Crypto Moonboys is where the movement, community and public record live. SWARMSY is where each creator privately develops the identity, project and intelligence behind their work.**

Crypto Moonboys repository:

`https://github.com/Crypto-Moonboys/Crypto-Moonboys.github.io`

## Product Mission

The internet gave everyone a voice, but not everyone has a clear identity, recognisable signal, practical direction or system for maintaining momentum.

SWARMSY exists to help people:

- discover or strengthen who they are publicly;
- clarify what they represent;
- create a memorable message and visual signal;
- turn rough ideas into controlled creative directions;
- explore more original possibilities without losing project truth;
- preserve accepted and rejected decisions;
- plan products, campaigns, stories, businesses and creator worlds;
- review proof, permissions, ownership and public claims;
- continue later without rebuilding context from zero;
- grow a private project intelligence system that becomes more useful over time.

The normal experience must not feel like developer software, an AI control panel or a generic model chat window.

It is intended for people who may know nothing about:

- models;
- prompts;
- providers;
- vector databases;
- agents;
- embeddings;
- collectors;
- workspace configuration;
- API routing.

The success test is not whether a technical feature exists.

The success test is whether a first-time, non-technical user can create, understand, approve, save and continue meaningful work without outside help.

## The Beginner Journey

The default experience must remain conversational, forgiving and clear:

1. The user chooses whether to build around themselves, build a hidden identity or bring in an existing project.
2. SPARKY presents the full question set in clear sections.
3. The user answers everything they can in one or several rough batches.
4. The app saves progress automatically.
5. SPARKY asks only important missing or unclear follow-ups.
6. Before the idea is created, the user chooses **WTF** or **SAFE**. If skipped, SPARKY defaults to WTF.
7. SPARKY creates a distinctive Identity Idea.
8. The user chooses **Keep**, **Delete** or **Try Another**.
9. A kept idea becomes a normal SPARKY brainstorming conversation.
10. The user may ask why, reject details, request changes or explore alternatives.
11. Nothing becomes an approved project idea until the user clearly asks to save it.
12. The approved idea is stored in the owning workspace and can be continued later.

Every Identity Idea must contain three simple hooks:

- **MESSAGE** — the line, belief or thought people should remember.
- **DOODAD** — the recognisable visual object, symbol, character or device.
- **PLACEMENT** — a fictional or legal concept-mockup setting that makes the message hit harder.

These hooks prevent an early idea from becoming an abstract strategy document with no memorable public signal.

## WTF and SAFE

WTF and SAFE are creative-intensity settings, not quality levels.

### WTF

WTF seeks maximum raw, unusual, provocative and disruptive creative energy while remaining:

- legal;
- non-hateful;
- non-harmful;
- grounded in the user’s actual identity and project.

### SAFE

SAFE produces a direction that is easier to approve, publish, share or commercialise.

SAFE must remain distinctive. It must not collapse into generic corporate branding.

A project may use both. For example, the user may develop a WTF concept and later ask SPARKY to create a SAFE presentation for a council, client, school, gallery, venue or investor.

## The SPARKY Contract

SPARKY is the permanent product agent inside every SWARMSY workspace.

A user may select Ollama, another local model or a configured API provider. That changes the supporting inference engine. It must not replace SPARKY, bypass SPARKY’s instructions or turn the workspace into a direct generic provider chat.

Every meaningful SPARKY reply must pass through:

- the SPARKY system prompt and behaviour contract;
- the current SWARMSY workspace;
- the owning-user and owning-workspace boundary;
- the user’s saved identity decisions;
- approved project state;
- relevant Memory Locks;
- stored continuity records;
- relevant Wiki Packs and uploaded documents;
- the selected provider as a supporting reasoning and generation engine.

Changing providers must never silently change the agent identity.

Provider names and technical configuration should remain secondary to the SPARKY experience.

## AnythingLLM and SWARMSY

AnythingLLM remains an important and visible foundation.

The product distinction must be clear:

- **Continue with SPARKY** — guided identity creation, project decisions, brainstorming, packs, Proof Review and saved continuity.
- **Open AnythingLLM** — advanced document work, deeper configuration and open-ended general AI assistance outside the guided journey.

AnythingLLM is the general capability and advanced environment.

SWARMSY is the controlled beginner product built on top of it.

The project must not hide or remove legitimate upstream attribution.

## Wiki Packs: Minimum Context, Not Complete Databases

Wiki Packs do not attempt to contain every answer.

They are intentionally small situational operating guides.

The underlying model and AnythingLLM provide broad intelligence, reasoning and document capability. A pack exists to tell SPARKY:

- what kind of situation the user may be entering;
- why the request may lead to real action;
- what facts, permissions or current conditions must not be assumed;
- what important questions should be asked;
- what risks, laws, ownership or safety issues may matter;
- what evidence and sources should be preserved;
- what action-ready output the user is probably trying to create.

Example: a legal-wall starter pack does not need to list every legal wall or contain every property record.

It may remind SPARKY to:

- establish the user’s location;
- verify that wall information is current;
- distinguish legal, commissioned, tolerated and unauthorised surfaces;
- identify who controls the property;
- avoid treating an online listing as permission;
- understand the intended artwork, scale and dates;
- consider access and public safety;
- prepare an owner or council request;
- preserve written approval and restrictions.

The model provides capability.

SPARKY provides responsibility and continuity.

The pack provides situational awareness.

Packs must not make SPARKY rigid. They should help it ask better questions and treat the user’s request with the correct seriousness.

## Action-Aware AI

A normal chatbot may interpret a message as casual curiosity.

SPARKY should recognise that the user may be preparing to act.

Where relevant, SPARKY should establish missing context such as:

- location;
- intended outcome;
- audience;
- ownership;
- permission;
- budget;
- timescale;
- public safety;
- evidence;
- legal or professional limits;
- what the user expects to do next.

SPARKY may help reason, research, organise, draft and prepare actions according to the tools and information actually available.

It must not:

- present stale information as current;
- treat inspiration as permission;
- treat a public-facing wall as publicly owned;
- claim a draft risk assessment has professional approval;
- describe a proposal or mockup as completed work;
- claim an email, booking, purchase, publication or external action occurred when it did not;
- use a connected write tool without explicit user intent;
- describe web search, file writing, scheduling, email or other action tools as live when they are not wired.

## User-Grown Project Intelligence

Every user may begin with the same small starter pack. They should not remain the same.

As the user creates, works and learns, their workspace may accumulate:

- approved identity decisions;
- visual and verbal rules;
- local laws and professional guidance;
- contracts and permissions;
- budgets and suppliers;
- campaign history;
- accepted and rejected methods;
- audience knowledge;
- collaborators and contacts;
- evidence and proof;
- project-specific sources;
- industry processes;
- lessons learned.

Over time, each workspace should become a different personal creator intelligence system.

A community mural organiser, anonymous artist, fashion creator, musician and local business may begin with similar starter material and develop completely different rules, packs, evidence and working methods.

The application does not mould every creator into one system.

It provides a controlled starting point and helps the user build the intelligence required by their identity, project, location, industry and future.

## Memory and Approval Rules

The selected model is not the source of truth for user memory.

Durable application storage is.

SPARKY acts as the user-facing memory manager, while the application owns persistence and access control.

Saved records must be scoped to both the owning user and owning workspace unless a separately specified single-user fallback applies.

The system must distinguish between:

- a suggestion SPARKY generated;
- an idea the user kept for discussion;
- changes discussed in chat;
- an idea the user explicitly approved and saved;
- a Memory Lock that must not be silently overwritten.

SPARKY must not silently overwrite an approved identity, Memory Lock or project state.

Material changes require clear user intent.

Delete actions must be understandable and deliberate.

A new chat thread must not automatically mean a new project.

## Memory Locks

Memory Locks preserve approved truths and boundaries, including where relevant:

- identity name;
- public message;
- privacy position;
- visual rules;
- project purpose;
- accepted and rejected concepts;
- ownership agreements;
- legal restrictions;
- character traits;
- campaign decisions;
- verified claims;
- facts that must not drift.

Memory Locks do not prevent exploration.

They allow stronger models to challenge and expand a project without accidentally erasing its foundation.

## Proof Review

Creative confidence must not become invented evidence.

SWARMSY must distinguish:

- idea;
- concept mockup;
- draft;
- proposal;
- approved plan;
- completed work;
- verified result;
- public claim.

Proof Review helps identify:

- what can safely be claimed;
- what needs evidence;
- what remains opinion;
- what is planned but not completed;
- what permission is missing;
- what source should be attached;
- what language is overstated.

Durable, user-and-workspace-scoped Proof Review storage and authenticated API access are shipped.

A fuller Proof Review history surface remains product work.

## Local Intelligence and API-Backed Intelligence

SWARMSY supports local and configured API-backed providers.

The difference is not that local AI follows the rules while connected AI ignores them. SPARKY, project state, packs, Memory Locks and user approval rules remain in control in either mode.

### Local mode

Local mode prioritises:

- privacy;
- user control;
- local continuity;
- reduced dependence on paid external services.

Its creative and reasoning depth depends on the selected model and available hardware.

Smaller local models may produce:

- more obvious ideas;
- safer directions;
- weaker cultural combinations;
- shorter reasoning;
- more predictable branding;
- less confident strategic challenge.

Stronger local models may perform substantially better.

### API-backed mode

A stronger connected model may provide:

- deeper reasoning;
- wider cultural pattern recognition;
- stronger strategic challenge;
- more surprising combinations;
- better interpretation of ambiguity;
- longer context handling;
- broader current research or tool capability where actually connected.

The API provider does not replace SPARKY.

It raises SPARKY’s reasoning ceiling.

The project must not promise identical quality, context limits, knowledge freshness or tool capability across every provider.

## Workspace Identity and Boundaries

Workspaces created by the SWARMSY flow are **SWARMSY/SPARKY workspaces**, not generic AnythingLLM workspaces.

The interface must make this unmistakable through naming, branding, navigation and explanatory copy.

A SWARMSY/SPARKY workspace must:

- be visibly identified as SPARKY-led;
- preserve the SPARKY behaviour contract regardless of provider;
- keep user and workspace data correctly isolated;
- store approved ideas and continuity in durable application storage;
- resume the user’s project without requiring reconstruction of prior chat context;
- keep internal implementation language out of the normal journey;
- allow advanced AnythingLLM access without letting it take over the default SWARMSY experience.

## Beginner-First Interface Rules

New user-facing work must:

- prefer ordinary language such as **Start**, **Continue**, **Keep**, **Delete**, **Try another** and **Save this idea**;
- present intake questions in clear sections;
- accept full or partial answer batches;
- ask one clear follow-up at a time only where something important is missing;
- explain why a question matters only where useful;
- save progress without requiring a technical action;
- provide a safe way to skip, go back, change an answer or try again;
- hide model, prompt, doctrine, collector, embedding, database and routing terminology from the normal journey;
- perform safe setup automatically where possible;
- translate setup failures into plain recovery instructions;
- keep advanced controls separate from the beginner path;
- never require normal users to paste internal prompts or operate developer tools.

7. Durable memory belongs to the application and remains scoped safely by user and workspace.
8. Starter Wiki Packs remain minimum situational guidance rather than attempts to duplicate the model’s general knowledge.
9. Workspaces are allowed to become different through user-grown project intelligence.
10. Local and API-backed model capability must be described honestly.
11. SPARKY should recognise potentially actionable requests and gather relevant context without becoming rigid.
12. Advanced AnythingLLM capability remains available without taking over the default journey.
13. Technical implementation details must not leak into ordinary user copy without a genuine recovery need.
14. Infrastructure work must support the end-to-end user journey rather than substitute for completing it.
15. Crypto Moonboys must remain visibly connected as the public movement and knowledge world, not treated as an unrelated marketing site.

## Developer Quick Start

Requirements:

- Node.js 18 or newer;
- Corepack/Yarn;
- Ollama for the Local User chat path.

```bash
git clone https://github.com/HODLKONG64/DIZ-A-REMIX.git
cd DIZ-A-REMIX
corepack enable
corepack prepare yarn@1.22.22 --activate
yarn setup
yarn dev
```

`yarn dev` starts the server, frontend and collector together.

Use `dev:server`, `dev:frontend` and `dev:collector` when debugging one service.

## Windows Desktop Beta

Validate the desktop foundation without installing Electron:

```bash
yarn desktop:smoke
```

`desktop:dev` is a contributor-only shell launcher. It requires a local Electron shim, which is intentionally not installed by the normal setup path.

To test the shell with the Electron version used by the artifact workflow:

```bash
npm install --no-save --package-lock=false electron@33.4.11
yarn desktop:dev
```

Normal Windows testers should use the packaged artifact or installer instead of the contributor launcher.

The desktop build remains beta until the current release process proves clean installation, installed launch, runtime startup, database setup, frontend loading and uninstall behaviour on clean Windows environments.

Current public caveats:

- builds are unsigned;
- automatic updates are not implemented;
- broader clean-machine acceptance remains necessary.
